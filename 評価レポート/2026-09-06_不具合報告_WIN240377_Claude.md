## ① `inverse_square.py` が「計算済みなのに結果を見つけられない」

**症状**

既定の手順（条件入力の「条件（シート）」を選ばずに計算 → `inverse_square.py`）で、
計算は正常に終わっているのに次のように出て、**何も書き出されない**。

```
[逆二乗] 条件『現状』
[逆二乗] 音圧レベルのまとめが見つかりません（先に計算してください）
[逆二乗] 0 条件ぶん書き出しました
```

「先に計算してください」と言われるが、`結果\<室>_まとめ_音圧レベル.csv` は実在する。

**再現手順**

1. `project.json` の `condition_sheet` が空のまま計算する
   （★これは**異常な状態ではなく GUI の既定**。`setup_window._refresh_sheets`
   がコンボボックスの先頭に空欄を置き、選ばなければ空のままにする。
   コメントにも「選ばなければ結果ファイル名に条件名を付けない」と意図が書いてある）
2. プロジェクト直下に `条件表.xlsx` がある（計算時に無ければ自動で作られるので、
   ふつうは必ずある）
3. `python inverse_square.py "<プロジェクト>"` を実行する

`test.dxf` で実際に踏んだ。

**原因（見立て）**

書く側と読む側で、ファイル名に付く**条件名の有無が食い違う**。

- **書く側**：`run_project` は `project.condition_sheet`（空）をそのまま使うので、
  `condition_label` が空 → `test_まとめ_音圧レベル.csv`
- **読む側**：`inverse_square.main()` が条件表のシートを全部数え上げ、
  `project.condition_sheet = "現状"` を**自分で立てる**
  （`geosim/inverse_square.py:484-491`）→ `test_現状_まとめ_音圧レベル.csv` を探す

このリポジトリには本来この食い違いを吸収する仕組みがある。
`Project.name_candidates()` が ①室名＋条件名 → ②室名だけ → ③頭なし の順に探し、
コメントにも「★②があるのが大事。条件表を作った瞬間に条件名が付くので、
それ以前の結果が読めなくなってしまう」と書いてある。

ところが `read_levels()` だけ、この仕組みを通さず `prefixed()` で 1 通りだけ組んでいる。

```python
# geosim/inverse_square.py:107-114
def read_levels(project):
    """`まとめ_音圧レベル.csv` から (周波数, {受音点名: Lp[バンド]})。"""
    import summary as sm

    path = os.path.join(project.folder, pj.RESULT_DIR,
                        project.prefixed(sm.LEVEL_FILE))   # ← ここ
    if not os.path.exists(path):
        return None, {}
```

すぐ上の `read_points()`（`geosim/inverse_square.py:75-79`）は
`project.existing_result_path("points")` を使っていて、**同じファイルの中で流儀が割れている**。

**確認**

`project.json` の `condition_sheet` を `"現状"` にして計算し直すと、
まとめ表が `test_現状_まとめ_音圧レベル.csv` になり、`inverse_square.py` が通る。
→ 診断のとおり、**名前の食い違いだけが原因**。

```
[逆二乗] 表を書き出しました: …\結果\test_現状_逆二乗.csv
[逆二乗] 1 条件ぶん書き出しました
```

**修正案（未適用）**

`read_levels()` を `name_candidates()` 経由にすれば、他の読み口と揃う。

```python
for name in project.name_candidates(sm.LEVEL_FILE):
    path = os.path.join(project.folder, pj.RESULT_DIR, name)
    if os.path.exists(path):
        break
else:
    return None, {}
```

**当座の回避**

条件入力の「条件（シート）」で**シートを明示的に選んでから**計算する。
あるいは `python inverse_square.py "<フォルダ>" --sheet ""` … は不可
（`--sheet` を省略すると全シートを数え上げる作りなので、「条件名なし」を指定する道が無い）。

**影響の範囲**

- `report_inverse_square.py` は `inverse_square.run()` を呼ぶので**同じ症状**になるはず（未確認）。
- 逆二乗の評価は半無響室・無響室の確認に使う「別ルート」なので、通常の
  残響時間・音圧レベルの計算結果そのものには影響しない。

## ② 条件名の付け方が、ツールによって食い違う（軽微・要判断）

①と同じ根の話。`condition_sheet` が空のとき、**同じプロジェクトの同じ条件**なのに
出てくるファイル名が割れる。

| ツール | 条件シートの扱い | 出るファイル名 |
|---|---|---|
| `run_project.py` | `project.condition_sheet` のまま（空） | `test_まとめ_音圧レベル.csv` |
| `mode_shape.py` | 同上（空） | `test_音圧分布_01_….csv` |
| `frequency_response.py` | **全シートを数え上げて立てる** | `test_現状_伝達関数.csv` |
| `inverse_square.py` | **全シートを数え上げて立てる** | `test_現状_逆二乗.csv` |

実際に 1 つの `結果\` フォルダの中で、`test_…` と `test_現状_…` が混在した。
どちらに揃えるかは方針の話なので、**判断をお願いします**（勝手に寄せません）。

- 案 A … 数え上げる側（`frequency_response` / `inverse_square`）を
  「プロジェクトが条件シートを持っていなければ立てない」に揃える
- 案 B … `run_project` 側で、条件シートが空でも先頭のシート名を条件名として採用する
  （※ただし `Project.condition_label` のコメントにある
  「既定名は条件を分けていないということなので空にする」という設計判断と衝突する）

## ③ 一括実行のあと `project.json` の条件シートが最後の条件に書き換わる（軽微）

**症状**

「全条件を一括 ▶▶」（`run_project.py --conditions`）で回すと、
条件入力で選んでいたシート（例：`現状`）に関わらず、
`project.json` の `condition_sheet` が**最後に回した条件**（例：`対策案`）になる。
次に画面を開くと、選んでいたつもりの条件と違うものが選ばれている。

**原因（見立て）**

`run_conditions()` は条件ごとに `sub`（`Project` の複製）を作るが、
`folder` は同じなので、`run(sub)` の中の
`project.save()`（`geosim/run_project.py:34`）が
**その条件の設定で `project.json` を上書きする**。ループの最後の条件が残る。

```python
# geosim/run_project.py:219-222（条件ごとの複製。folder は同じ）
sub = pj.Project(project.folder, **{k: getattr(project, k) for k in pj.DEFAULTS})
sub.condition_csv = file_name
sub.condition_sheet = sheet or ""
```

**影響**

計算結果そのものは正しい（条件ごとに正しい名前で出る）。
気づかずに次の単発計算をすると、意図と違う条件で回ることになる。
`mode_shape.py` / `frequency_response.py` / `inverse_square.py` も
`condition_sheet` を自分で立てるので（②参照）、同じ道筋で書き換わりうる。

**当座の回避**

一括実行のあとに単発で回すときは、条件入力の「条件（シート）」を選び直す。
