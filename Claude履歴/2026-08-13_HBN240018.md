## 逐次ログ

### 1. 開いた形状（閉じていない形状）での計算に対応

**ユーザー指摘**：「閉じていない場合でも計算ができるような仕組みなはず。
一面だけ壁があって直接音と1回反射音だけが到来する状況も検証できたはず」→ **指摘は正しかった**。

#### なぜ開いた形状でも計算できるのか

面は `v·n < 0`（法線に向かって進む）のときだけ衝突と判定する → **片側だけ反射する**。
法線の裏から来た音線は通り抜ける。当たる壁がなくなった音線はそこで打ち切られる。
この片側性のおかげで閉じた室である必要がない。

#### 検証結果

| ケース | 結果 |
|---|---|
| 一面の壁（法線+z）／音源・受音点とも法線側 | **反射回数 0 と 1 のみ**。直接音 2.000 m と 1回反射 2.828 m（虚音源 (0,0,−1)）。重複削除後ちょうど **2 経路** |
| 同じ壁／音源・受音点を裏側に | 直接音のみ |
| **法線を逆向きにして音源を法線の反対側に** | **直接音のみ。反射音が消える** ← 危険なケース |
| 床＋垂直壁の二面 | 0/1/2 回反射（コーナー反射）。重複削除後 4 経路 |
| 3DFACE の一面反射板 DXF | 直接音 4.000 m ＋ 1回反射 4.472 m のちょうど 2 経路 |

#### 元コードの確認（backtrace.f90 262〜282行）

Fortran は法線を外積で計算したあと、**`ynnmrev` という y/n フラグで全反転するかを
ユーザーに聞くだけ**だった（自動判定はしていない）。
つまり私が入れた `'auto'` は移植ではなく独自追加で、そこに閉形状の前提が紛れ込んでいた。

#### 修正内容

- `open_edge_count()` を新設。**開いた辺（三角形1枚にしか属さない辺）の本数**で閉/開を判定
  （閉じた多面体では全ての辺がちょうど 2 枚に共有される）
- `'auto'`：**閉じていれば**符号付き体積で内向きに揃える／**開いていれば何もしない**
- `'flip'` を追加（**元コード `ynnmrev='y'` に相当**）
- `DxfModel` に `is_closed` / `open_edges` / `volume` を追加し `summary()` に表示

### 2. 法線の向きの方針を訂正（面ごとの補正を廃止）

**ユーザーからの重要な訂正**：「法線が音の来る側を向くようにするのはまずい」。
凸凹の壁や宙に浮いた家具の衝突判定がバグる。私が 1 で追加した `orient_normals='toward'`
（面ごとに音源方向へ向ける）は**危険な機能だったので廃止**した。

#### 確定した方針

**法線は「音が通る空気側」を向く。その正解を持っているのは CAD モデル自身。**

- 室の外殻 → 室内向き ／ 室内に置く物体（机・什器）→ 外向き ／ 一面反射板 → 反射させたい側
- **両面で反射させたいものは CAD 側で厚みを持たせる。**
  室内の厚みのある机（脚は省略）なら **上面は上向き法線、下面は下向き法線**となり、
  どちらも空気側を向く。1 枚の面では片側しか反射しないので厚みが必要
- **最終的には GUI 上で法線の向きを調整できるようにしたい**（ユーザー要望 → TODO G-8）

#### 修正内容

- **既定を `'auto'` → `'cad'` に変更**。読み込み側は勝手な補正をしない
- **`'toward'` / `'away'` / `'inward'` / `'outward'` / `'auto'` を廃止**（`ValueError`）
- 残したのは `'cad'`（既定）/ `'flip'`（全反転）/ `'shells'`（シェル単位で空気側へ揃える）の 3 つ。
  `'shells'` は面ごとにいじるのではなく**閉じたシェル単位で一括反転**するので凸凹があっても壊れない
- **シェル診断を新設**（勝手に直すのではなく、誤りを可視化する方向へ）
  - `mesh_shells()` … 辺の共有で連結成分（シェル）に分割
  - `analyse_shells()` … シェルごとに 閉/開・体積・法線の向き・外殻かを返す
  - `winding_is_consistent()` … 同じ有向辺が 2 回現れないかで巻き順の一貫性を判定
  - `summary()` がシェルごとに「OK」「★要確認（outward が空気側）」まで表示
  - 結果は `DxfModel.shells` / `.winding_consistent` に入る → **GUI の土台（G-8）**

#### 検証（室 4×5×3 m ＋ 厚みのある机 1.6×0.8×0.05 m を 3DFACE で生成）

| 項目 | 結果 |
|---|---|
| 机の上面 / 下面の法線 | **+z / −z（どちらも空気側）** |
| 机の上面・下面の両方で反射しているか | **両方 True** |
| シェル診断 | 外殻 体積60.0000m³ 法線=inward OK ／ 内側 体積0.0640m³ 法線=outward OK |
| 机あり／なしの経路数 | 583 / 558 経路（机が遮蔽・反射を生んでいる） |
| 凸部（角柱）を壁に貼った形 | 面ごとに ±x,±y,±z の 6 方向。`'cad'` はそのまま保持 |
| 机の法線を誤って内向きにした DXF | `'shells'` で上向きに自動補正できる |

`docs/DXFデータの作り方.md` 3節と `docs/技術説明書.md` 3.3節を全面的に書き直した
（「法線が音の来る側を向くようにする」→「法線が空気側を向くようにモデルを作る。
両面反射させたいものは厚みを持たせる」）。厚みのある机の断面図も追加。

### 3. 多角形→三角形分割の堅牢化

**ユーザー質問**：「モデルの要素は三角形要素を考えているが、多角形を三角形要素に変換するのは大変では？」
→ **大変ではない。CAD 側で三角形に割る必要もない。**

#### 堅牢化した内容（素朴な扇状分割の穴を塞いだ）

| 問題 | 対処 |
|---|---|
| **凹んだ四角形** | 素朴な扇状分割だと多角形の外に三角形ができる。`_diagonal_is_inside()` で**内側を通る対角線を自動で選ぶ** |
| **ねじれた四角形** | どちらの対角線で切るかで形が変わる。`quad_warp()` で平面からのずれを測り**警告** |
| 5 角形以上 | 耳刈り法を実装 |
| 3DFACE の重複頂点 | `_dedupe_consecutive()` で連続重複を落とす |

#### 検証で見つけた自分のバグ

凹み判定 `_diagonal_is_inside()` を最初 `< 0`（両側に厳密に分かれる）で書いたが、
**3 点が一直線に並ぶ退化ケース（符号が 0）で誤判定**して不要に対角線を切り替えていた。
`<= 0` に緩和（面積ゼロの三角形ができるだけで、残る三角形が多角形を正しく覆う）。

テストケースの作り方も 2 回間違えた。**凹み頂点が index 0 や 2 にあると扇状分割でも
正しい面積になってしまう**ので、破綻を再現するには凹み頂点を index 1 か 3 に置く必要がある。

#### 検証結果

| ケース | 結果 |
|---|---|
| 平面の凸四角形（1×1） | 三角形 2 枚 / 面積 1.000000 |
| 凹四角形（凹み頂点 index 1） | 扇状分割 3.000000（誤） → **修正後 1.000000**（靴ひも公式と一致） |
| 退化した凹四角形（3点一直線） | 1.000000（うち 1 枚は面積 0 で後段が捨てる） |
| 五角形（耳刈り法） | 三角形 3 枚 / 面積 5.250000（一致） |
| test.dxf 回帰 | 三角形 12 枚 / 表面積 22.0000 m² / 体積 6.0000 m³ |

※このとき「DXF から入ってくる面は最大 4 頂点」と書いたが、翌項で**誤りになった**（閉じたポリラインなら何角形でも来る）。

### 5. ねじれ報告の実寸化と AutoCAD での作図方法

**ユーザー質問**：「ねじれのない面を作るにはどうモデル化すべきか？ポリラインではなく面として作成すべきか？」

#### 回答：面エンティティにしてもねじれは直らない

3DFACE もポリフェイスメッシュも頂点ごとに z を持てるので、4 頂点なら同じようにねじれる。
効くのは**構造的に平面が保証される描き方をすること**。保証の強い順に：

| 作図方法 | 平面性 | 理由 |
|---|---|---|
| **三角形で作る** | **原理的に必ず平面** | 3 点は必ず 1 つの平面を張る |
| **UCS を作業面に合わせて `PLINE`**（LWPOLYLINE） | **構造的に必ず平面** | 頂点が xy のみ、高さはエンティティ全体で 1 つ（グループコード 38）。ねじれる余地がない |
| **直線の辺を押し出す**（`EXTRUDE` / 立ち上げ） | **必ず平面** | 直線 + 平行移動は必ず 1 つの平面を張る |
| 平面で描いてから `3DROTATE` / `ALIGN` | 保たれる | 剛体変換は平面性を壊さない |
| `3DPOLY` / `3DFACE` で 3D 空間に直接描く | **ねじれうる** | 頂点ごとに z を持てる。`test2.dxf` はこの形式 |

推奨手順（傾いた面）:
```
UCS → 3P（3点指定）または UCS → OB（既存面）で作業面を決める
PLINE で閉じた輪郭を描く   ← LWPOLYLINE になるので平面が保証される
UCS → W（ワールドに戻す）
```

**AutoCAD 内での平面性チェックの裏技**: `REGION` は定義上「平面領域」なので、
**平面でない閉じた輪郭には失敗する**。平面性の検算に使える
（確認後は REGION を削除してポリラインのまま書き出す。REGION 自体は本ツールでは読めない）。

#### 実装の改善：ねじれ報告を実寸（mm）化

相対値だけでは「直すべきか」が判断できなかったので、**実寸 mm と影響の目安**を出すようにした。

1 m 角の面での影響（法線の傾き → 10 m 先での音線のずれ）:

| ねじれ | 法線の傾き | 10m 先のずれ | 判断 |
|---|---|---|---|
| 0.05 mm | 0.003° | 1 mm | 無視できる（スナップの丸め程度） |
| 0.5 mm | 0.029° | 10 mm | 無視できる |
| 5 mm | 0.29° | 100 mm | 受音球半径と同程度。気になるなら直す |
| 50 mm | 2.9° | 1000 mm | 作図ミスの可能性が高い |

受音球の半径は通常 50〜300 mm なので、**ねじれ 1 mm 程度なら音響的には無視できる**。

### 6. モデルビューアの作成

**ユーザー依頼**：読み込んだモデルを GUI で表示。三角形要素になっていること・法線の向きが
分かる表示・回転等ができること。→ `geosim/view_model.py` を新設。

#### 実装方式の選択：自己完結 HTML + WebGL

**この環境には matplotlib / pyvista / vtk / PyQt5 / PySide6 / plotly / scipy が
すべて入っていなかった**（`tkinter` のみ）。`pip install` を勝手に走らせたくないので、
**依存ゼロで動く自己完結 HTML（WebGL）を書き出してブラウザで開く方式**にした。

副次的な利点：出力①②（音線・音粒子アニメーション）を載せる土台になり、
GUI（G-7）を Web ベースにする場合はそのまま発展させられる。
デスクトップアプリ路線にするなら別途方針決定が必要（`pip install pyvista` など）。

```
cd geosim
python view_model.py ..\test2.dxf --absorption ..\absorption.csv
```

#### 表示内容

| 要素 | 表現 |
|---|---|
| 三角形要素 | 面 + **辺を描く**ので分割が見える |
| 法線 | 重心から伸びる矢印（矢じり付き。長さはモデル対角の 6%） |
| **法線の向き** | **裏側（法線と反対から見ている側）を赤で塗る** ← 向きの誤りが一目で分かる |
| レイヤ | 色分け + 表示/非表示の切り替え |
| 音源・受音点 | 赤 / 青の点 |
| 読み込み結果 | `DxfModel.summary()` をパネルに表示 |

操作：ドラッグで回転、ホイールで拡大縮小、右ドラッグ（または Shift+ドラッグ）で平行移動、
視点プリセット（等角 / 上 / 正面 / 側面）。

#### 実装上の要点（後から触るとき用）

- **表裏の判定は `gl_FrontFacing`（頂点の巻き順）ではなく、保持している法線と視線の内積**で行う。
  読み込み側は巻き順を変えずに法線だけ反転することがあるため、巻き順で判定すると嘘になる
- **レイヤの表示切り替えは、頂点をレイヤ順に並べて描画範囲を飛ばす**方式。
  当初シェーダの uniform 配列を動的インデックスする実装にしたが、
  GLSL ES では移植性に不安があるので書き換えた
- 真上視点（仰角90°）は up ベクトル [0,0,1] と視線が平行になり lookAt が退化するので
  0.02 rad 傾けてある
- 初回描画は `requestAnimationFrame` 経由（`canvas.clientWidth` が 0 のまま描かないように）
- 出力 HTML は再生成できるので `.gitignore` で除外（`*_view.html`）

#### 検証（ブラウザ・node が使えないので静的検査で代替）

- データの整合性: 三角形12枚/9枚、positions/edges/arrows の個数、法線が全て単位ベクトル、
  3頂点に同一法線（フラットシェーディング）、**矢印が全面で重心から法線方向へ伸びている**、
  bbox の一致、レイヤの描画範囲が隙間なく並んでいること
- 静的検査: `getElementById` の対象が HTML に存在するか、`querySelector` のセレクタが該当するか、
  シェーダの attribute/uniform 名の双方向照合、未定義関数の呼び出し、括弧の対応、
  `gl.drawArrays` のモード
- 検査スクリプトの不具合も 2 件直した（`const DATA = ` のスペース、
  文字列除去前に関数呼び出しを走査してシェーダの GLSL 関数を拾っていた）
