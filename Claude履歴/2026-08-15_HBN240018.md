## 1. 法線の自動判定 `orient_normals='auto'`

昨日（8/14）実装した `'inward'`（レイの偶奇で内向き判定）を、
**閉じているかどうかで自動的に使い分ける**ようにした。

```
'auto' の分岐
  ├ 閉じていて巻き順も一貫  → 'shells'（外殻は内向き、内側の物体は外向き）
  ├ 囲まれている            → 'inward'（面ごとにレイの偶奇で内向きへ）
  └ 開いた形状              → 'cad'（触らない）
```

**「囲まれているか」を実際に測る**のが要点（`encloses_point()`）。
判定したい点から全方向へレイを飛ばし、面に当たった割合を返す。
閉じた室の内側なら 1.0、一面反射板なら 0.5 前後、外側なら 0 に近い。しきい値は 0.95。

なぜこれが要るか：**開いた形状に内向き補正をかけると、一面反射板の
反射させたい側が逆になる**。「閉じているか（開いた辺が 0 本か）」だけで
判定すると、研修室のような板の寄せ集め（開いた辺 136 本）が漏れる。
逆に無条件に内向き補正をかけると一面反射板が壊れる。
実際に囲まれているかを測れば両方さばける。

検証（3 モデルとも期待どおり）:

| モデル | 判定 | 結果 |
|---|---|---|
| 研修室（板の寄せ集め、開いた辺 136 本） | 囲まれ度 1.00 → `inward` | 70 枚中 36 枚を反転、全面内向き |
| test.dxf（閉じた直方体） | 閉じている → `shells` | 反転 0 枚（もともと正しい） |
| test2.dxf（開いた形状） | 囲まれ度 0.37 → `cad` | 触らない |

## 2. 法線の確認・修正ウィンドウ（`normal_editor.py`、G-8 完了）

自動判定に任せきりにせず、**人が見て確認し、必要なら反転できる**ようにした。

| 色 | 意味 |
|---|---|
| 緑 | 法線が室内（空気側）を向いている |
| 赤 | 法線が室外を向いている。反転が要る |
| 灰 | 判定できない（開いた形状など）。CAD の指定を尊重する |

操作は「枠で囲んだ面を反転（`enable_cell_picking(through=False)` で手前の面だけ拾う）／
数字キーでレイヤごと反転／`a` 自動／`d` CAD に戻す／`i` 全反転／`n` 法線矢印／`s` 保存」。
（視点キー z/x/c/v と衝突したので、当初の c / x から d / i に変えた）

**状態は `flipped`（CAD の巻き順から反転する面のインデックス集合）ただ 1 つ**にした。
`read_model(flip_faces=...)` にそのまま渡せる形で、自動判定の結果もここに畳み込んで
保存するので、**保存したものを読めば再現できる**。
適用の順序は「自動判定 → 手動指定」で、**人が直したぶんが最後の決定**になる。

保存先は `normals.json`。**書いたときの DXF と面数を控えてある**ので、
DXF を差し替えて面数が変わったら使わずに知らせる
（黙って間違った面を反転させると原因の分からない不具合になるため）。

## 6. 明瞭度の指標（`reverberation.clarity_measures()`、G-4 完了）

残響指標が「どれだけ長く響くか」なのに対し、こちらは
「**初期の音が後から来る音に対してどれだけ強いか**」。会議室・教室で効く。

| 指標 | 定義 | 用途 |
|---|---|---|
| C50 | `10 log10( ∫₀^50ms p² / ∫_50ms^∞ p² )` [dB] | 音声 |
| C80 | 同上、境目 80 ms [dB] | 音楽 |
| D50 | `∫₀^50ms p² / ∫₀^∞ p²` [0〜1] | 音声（C50 の言い換え） |
| Ts | `∫ t·p² / ∫ p²` [s] | 重心時刻。小さいほど明瞭 |

**時刻の起点は直接音の到来時刻**にした。音源から受音点までの伝搬時間ぶん、
インパルス応答の先頭には無音があり、そこを含めると 50 ms の窓がずれる。
各バンドでエネルギーが最大になる時刻を直接音とみなしている。

検証：直接音のみなら D50 = 1.0000、既知の指数減衰で解析値と 0.03 以内、
`C50 = 10log10(D50/(1-D50))` の関係が 0.05 dB 以内で成立。

## 追記：法線の二重反転の不具合（同日中に発見・修正）

GUI を一通り動かしてもらったあと、結果を見たら **T30 が 0.487 → 0.233 秒**と
半分近くに変わっていた。原因は法線の**二重反転**。

### 何が起きていたか

`normal_editor` が保存する `flipped_faces` は
「**CAD の巻き順から反転する面**」の**絶対集合**で、自動判定の結果もそこに畳み込まれている。
一方 `read_model(flip_faces=...)` はそれを**自動判定への差分**として扱い、
上からトグルしていた。

```
自動判定  : 面 36 枚を反転（内向きに揃う）
保存内容  : その 36 枚（絶対集合）
読み直し  : 自動が 36 枚反転 → 手動指定が同じ 36 枚をもう一度反転 → CAD に逆戻り
```

結果として法線が半分外向きのまま計算され、音線が壁をすり抜けて残響時間が短く出ていた。

### 直し方

**`flip_faces` が渡されたら自動判定を丸ごと置き換える**（差分ではなく絶対集合）。
保存したものを読めば必ず同じ法線になる。

### なぜテストで捕まらなかったか

往復のテストを書いていなかった。書いていても、
**`test.dxf` も `test2.dxf` も自動反転が 0 枚**なので二重反転を踏まない。
`orient_normals='flip'`（全 12 枚を反転）で往復するケースを足して、
実際に反転が起きる状態で確かめるようにした。

追加したテスト（4 件）:

- 自動判定を保存して読み直すと同じ法線になる（test.dxf / test2.dxf）
- **反転が起きるモデルでも保存→読み直しで同じ法線になる**（これが捕まえる）
- 人が直した指定が自動判定より優先される

実モデルでの確認：`normals.json` の 36 枚と自動判定の 36 枚が一致し、
保存指定で読んだ結果が 70/70 面とも室内向き。T30 も 0.487 秒に戻った。

### ついでに直したもの

- **`decay.csv` が 13.8 MB あった**。Schroeder 逆積分は滑らかな単調減少なので
  44.1 kHz の分解能で持つ意味がない。1 ms 刻みに間引いて **315 KB** に。
  間引き後の CSV から読み直した T30 は元データと 0.002 秒以内で一致する
  （残響指標そのものは間引く前のデータから求めているので、この設定に依らない）
- `_sub_project()` が受音点 2 点目のフォルダを先に作っていたため、
  受音点が 1 つしかないのに空の `rec2/` が残って紛らわしかった。

## 追記2：画面構成の作り直しと、表示本数の調整（ユーザー指摘 4 件）

### 指摘 1「法線確認の画面が透過されていないので分からない」

法線エディタは 1 枚の PolyData をそのまま不透明で描いていたので、
**手前の壁に隠れて奥の面の向きが見えなかった**。

- 面を**レイヤごとの PolyData に分けて**持つようにした
  （レイヤ単位で表示 ON/OFF と不透明度を効かせるため）
- 既定の不透明度を 1.0 → **0.55**
- 音線ビューアと同じ `add_opacity_control` とレイヤのチェックボックスを載せた

### 指摘 2「音線と音粒子が片方向にしか飛んでいない。エラー？」

**計算は正常。表示の絞り方の問題だった。** 数字で確かめた。

| | +x / +y / +z の本数 | 平均方向の長さ |
|---|---|---|
| 記録した全音線 2000 本 | 1001 / 995 / 1000 | **0.000** |
| 生成直後（参考） | 1000 / 1000 / 1000 | 0.000 |

（平均方向の長さは 0 なら全方向へ均等、1 なら一方向に偏り）

粒子も 3.36 ms の時点で音源から半径 0.846〜1.155 m に分布し
（c·t = 1.155 m と一致）、平均方向の長さ 0.001 で等方だった。

見た目が偏って見えたのは **60 本しか描いていなかった**ことと、
`--received-only` で受音経路だけに絞っていたため。

ただし**本当に偏る作りになっていた箇所**も見つけて直した。
本数を減らすときに**先頭から N 本取ってはいけない**。
音線は Fibonacci 螺旋なので**添字に対して z が単調増加**し、
先頭から取ると天頂付近の帽子状に偏る。`even_subset()` で等間隔に抜くようにした。

### 指摘 3「見せる音線・音粒子の数を調整できるように」

- **候補**（`--pool`、既定 2000）を抱えておき、**実際に見せる本数はスライダで決める**
- 音線は `RayDisplay` が折れ線を作り直す（数百本なら一瞬）
- 音粒子は**点の数を変えずにエネルギーを NaN にして隠す**（`nan_opacity=0`）。
  トポロジを作り直さないので速い
- 起動時の本数は `--max-rays`（既定 60）/ `--max-particles`（既定は候補すべて）

### 指摘 4「レイヤ設定・透過率・操作説明が重なっている。左右に分割してよい」

**ウィンドウを左右に分けた**（左 1/4 が操作パネル、右 3/4 が 3D）。
`pv.Plotter(shape=(1,2), col_weights=[0.25, 0.75])` の 2 レンダラ構成。

`view_model_gui.ControlPanel` が**上から順に積む**ので要素が重ならない
（y 座標を手で決めていたのが重なりの原因だった）。

### この作り直しで踏んだ落とし穴（3 つとも実際に画面が壊れた）

| 症状 | 原因 | 直し方 |
|---|---|---|
| **音線がパネルの中に描かれた** | スライダは**生成時にコールバックを 1 回呼ぶ**。そのときパネル側のレンダラが選ばれていたので、音線の作り直しがパネルに入った | 生成時の 1 回を無視し、以降は必ず 3D 側を選んでから呼ぶ |
| チェックボックスとスライダが 3D 側に出た | ウィジェットは**そのとき選ばれているレンダラのビューポート**基準 | 置く前にパネル側を選ぶ |
| 文字どうしが重なった | VTK は**渡した位置がブロックの下端**で上へ書く。さらに行の高さを 15 px と見積もっていたが実際は約 18 px | 高さを引いてからその位置に置く／行高をフォントサイズの 2 倍で見積もる |

長いレイヤ名がパネル幅で切れる件は、`ControlPanel.fit()` で
**末尾を … にして収める**ようにした（途中で切れて読めないより良い）。

時刻表示はウィンドウ幅からの相対位置で右上に置いていたが、
レンダラを分けたらビューポートからはみ出して切れたので、パネルへ移した。
